# 구현 순서와 완료 기준

규격과 Fixture를 먼저 고정하고, 1 hop을 끝까지 연결한 뒤 3 hop·패턴으로 넓히고, 마지막에 실제 Snapshot과 장애 상황을 검증합니다.

## 구현 순서

| 단계 | 내용 |
| --- | --- |
| 1 | 규격·Fixture 고정 |
| 2 | 1 hop DB·API·화면 연결 |
| 3 | 3 hop·패턴·JSON 연결 |
| 4 | Snapshot·장애 검증 |

- 수집기는 분석·화면과 병렬로 개발한다.
- 통합 점검은 두 번 한다: 최초 1 hop 연결, 최종 P0 연결.

## 완료 기준

### 기능 연결

- [ ] 주소·Tx Hash 검색 → 그래프·목록 → 근거 상세 → JSON까지 이어진다.

### 데이터 모드

- [ ] 실제 테스트넷 수집과 Fixture 오프라인 실행이 모두 된다.
- [ ] 모드·버전·범위가 화면에 표시된다.

### 장애 대응

- [ ] 중복·청크 실패를 검증했다.
- [ ] 커밋 전후 중단·재시작·블록 해시 변경을 검증했다.
- [ ] `finalized` 초과 요청 거부와 RPC 범위 오류 시 청크 분할을 검증했다.

### 데이터 정확성

- [ ] 큰 uint256·다중 로그·시간 역전·다른 토큰을 올바르게 처리한다.
- [ ] 0값·0주소·자기 전송을 올바르게 처리한다.

### 탐색·패턴

- [ ] 탐색 상한과 부분 결과를 검증했다.
- [ ] 패턴의 599초·600초 경계와 고유 상대 수를 검증했다.
- [ ] 같은 입력에서 후보 경로 순서가 재현되고, `PATH_LIMIT` 잘림을 검증했다.
- [ ] 부분집합 패턴 제거와 `groupId` 묶음을 검증했다.

### 상태·응답

- [ ] 빈 결과·미준비·무효화·범위 밖을 구분한다.
- [ ] 이전 응답이 현재 화면·내보내기에 섞이지 않는다.

### 원천 대조

- [ ] 실제 전송 최소 10건을 Explorer·Receipt와 대조했다.

### 성능

- [ ] 합성 전송 10,000건·최대 3 hop·200노드·500간선 조건에서 API 응답 2초 이내를 실측했다.
- [ ] RPC 수집과 브라우저 렌더링 시간은 따로 측정했다.

### 실습

- [ ] 문제 3개와 비공개 정답을 준비했다.
  - CH1: 기본 경로
  - CH2: 분산·합류
  - CH3: 시간·토큰·미끼 경로
- [ ] 제출물 형식: 데이터셋 버전·경로 edgeIds·근거·한계.
- [ ] 채점: 경로 단위 집합 비교, 경로 안의 edge id 순서는 일치.

### 실행·기여

- [ ] 한 명령으로 실행되고 필수 문서가 준비됐다.
- [ ] 사용자 흐름 리허설이 2회 연속 성공했다.
- [ ] 팀원별 PR·문서·발표 기여를 기록했다.

## 데모 — 5~7분

1. 범위·모드 확인
2. 1 hop 분산 확인
3. 3 hop 후보 경로 확인
4. Transfer 근거 확인
5. 분산·합류와 오탐 설명
6. 미끼 경로 제외
7. 실제 Snapshot·Explorer 대조
8. JSON 내보내기
