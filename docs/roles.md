## 개발·인계

### 초기 고정

- 각 소유자가 자기 규격을 작성하고, 소비자가 비동기로 확인한 뒤 v1을 고정한다.
- 담당 3이 규격과 샘플을 취합한다.

### 개별 개발

| 담당 | 개발 환경 | 자체 검증 | 실제 연결 |
| --- | --- | --- | --- |
| 1 | 로컬 PostgreSQL·고정 Fixture·RPC Stub | DB 제약·Seed·재시작·Repository 테스트 | 실제 Repository 주입 |
| 2 | 고정 Fixture·요청 샘플 | Go 단위·회귀 테스트 | 실제 Engine 주입 |
| 3 | Fake Repository·Stub Engine·HTTP 샘플 | 핸들러·오류·직렬화·규격 테스트 | Repository·Engine 교체 |
| 4 | HTTP 샘플 기반 웹 Mock | Vitest·Playwright | API 모드로 주소 전환 |

- Mock·Stub은 개발·테스트 전용이다. 정식 실행은 실제 구현과 유효한 Fixture 또는 Snapshot을 쓴다.
- 개발 Fixture는 버전을 고정하고, 바뀐 데이터는 새 버전으로 제공한다.

### 담당 범위

- 담당 범위 안의 변경은 해당 담당자가 처리한다. 다른 영역의 변경은 이슈로 요청한다.
- 규격을 지키는 내부 구현·리팩터링·화면 배치는 소유자가 정한다.
- 규격 변경·보안 오류·통합 실패·일정 영향만 이슈로 협의하고, 이슈에 재현 입력과 로그를 붙인다.

### 리뷰·통합

- 기본 리뷰 짝: 담당 1 ↔ 2, 담당 3 ↔ 4.
- 주요 PR은 작성자 외 1명 이상의 승인을 받는다.
- 완료는 실제 구현을 연결한 테스트로 확인한다. 실제 연결 실패를 Mock 성공으로 대신하지 않는다.
